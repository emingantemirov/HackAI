# AuditFlow — five-minute pitch and demo

## Slide 1 / 30 seconds: The problem

“Requirements are spread across documents. Tests and expectations must stay aligned with
versions and software changes. The difficult part is preserving a checkable chain from a
requirement to an observed software result.”

## Slide 2 / 35 seconds: The solution

“AuditFlow connects sources, reviewed requirements, synthetic profiles, explicit test
expectations and evidence. AI drafts. People approve interpretations. Deterministic code
performs the supported comparisons.”

## Slide 3 / 35 seconds: The workflow

“Import a document, inspect the exact passage, draft a rule, review it, create a profile,
confirm the expected outcome, run a check and open the evidence. Versions and approvals
remain visible rather than being hidden inside a chat conversation.”

## Slide 4 / 90 seconds: Live demonstration

- Show a source and its pending requirement. Explain that the repository sources are synthetic.
- Show a prepared synthetic profile and confirm its scoped expectation.
- Run the synthetic 41 file and show the passed demo result.
- Repeat with the wrong-AZVU mutation. Open the failed comparison and evidence.
- Show the open-AU case as not assessable rather than inventing a counting rule.

Do not spend the entire pitch entering approvals. Prepare a separate disposable demo database
with your own documented demo-scope reviews before presenting. Keep shipped seed data pending.

## Slide 5 / 35 seconds: Changes and annual review

“New source versions identify directly affected requirements and tests. Keep the approved
baseline, rerun impacted tests and a core regression suite, and preserve historical reports.
The prototype demonstrates structural section comparison; broad legal impact analysis needs
additional dependency work.”

## Slide 6 / 40 seconds: What works and what remains

“Working: source import, draft generation, review gates, profiles, boundary drafts, fixture
checks, evidence, reports and the responsive UI. Automated checks and browser flows are
recorded in the repository. Remaining: successful live inference from the organizer network,
authoritative technical annexes and a real payroll-software connection.”

## Slide 7 / 35 seconds: The next pilot

“We propose one limited real-world pilot with an authoritative ruleset, independently
approved expectations and an actual vendor sandbox. Measure review effort, correction
cycles and defect detection before making savings or certification claims.”

## If the model/network fails

Use labelled offline literal candidates and the prepared synthetic cases. Say explicitly:
“This branch demonstrates the workflow without inference; live model connectivity was not
verified in this execution environment.” Never present literal splitting as a model output.

## Likely questions

**Does a green result certify software?** No, it covers only the documented checks and input.

**How do you prevent AI from marking its own wrong answer correct?** Independent expectation
review plus fixed checks; the current simulator still shares logic and is labelled as such.

**Why synthetic data?** Reproducibility and safe repository sharing; import originals locally
for a properly authorised, source-validated pilot.

**What does the annual audit get?** A versioned test baseline and a traceable report, with
final judgement remaining with the competent reviewer.
